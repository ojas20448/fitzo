Post-setup preference editing and training-only onboarding remain unfinished.

## Direction

Make Fitzo feel like a clear, practical training companion with its own identity. The user's feedback is that it looks generated by AI. Address that through hierarchy, useful content and specific language, rather than adding effects or more features. Keep Indian food support, Hinglish logging, workout tracking and buddies as strengths.

## First release: onboarding and clarity

### P0 — Resolve conflicting information

- [x] Replace the onboarding header's stale “1.6 g per kg” copy with the current goal-specific policy. Derive displayed values from the calculator instead of duplicating constants in prose.
- [x] Audit the coach's target source: nutrition editing uses `nutrition_profiles`, while the context pack previously read targets from `fitness_profiles`. Coach context now prefers nutrition values, with legacy fallback; isolated SQL regression checks pass. A live account walkthrough is still part of release verification.
- [x] Replace fixed weight-change projections with clearly labelled estimates, or omit them when the app cannot substantiate them.

Done when: changing a user's target produces matching values throughout the app and coach context; existing custom targets remain intact. Avoid a broad database migration until the actual read/write paths and existing records have been checked.

### P1 — A goal-first onboarding

Baseline before the 7 October implementation: onboarding started with body stats, optional body-fat percentage, BMI and a formula explanation. That flow is now replaced by four stages; the broader routine/training-first requirements below remain partly unfinished.

- [ ] Map and test the existing path on a phone before replacing it, including sign-up, returning unfinished users and completion.
- [ ] Use four short stages with related questions grouped together:
  1. **Your goal:** “What would you like to work on?” Lose fat, build muscle, maintain, or focus on training. Explain what the choice changes.
  2. **Your routine:** training experience, available days, session length and gym/home equipment. Ask follow-up questions only when they affect the plan.
  3. **Relevant basics:** measurements needed for nutrition estimates, units and typical activity. Explain why each is needed. Put optional body-fat input and detailed calculations outside the main path. Allow training-first users to finish nutrition setup later.
  4. **Your starting plan:** show a real first workout, weekly schedule and nutrition targets where applicable, with simple edit controls and a short explanation of how the answers affected them.
- [ ] Finish with “Start my first workout” or “Log my first meal,” selected by the user's intent.
- [ ] Save progress, support Back without losing answers and make optional steps clearly skippable. Do not invent silent defaults for missing required estimates.
- [ ] Offer health connection and notifications when their benefit is relevant, after the user has seen value. Use native permission requests and respect refusal; neither connection should block ordinary logging.
- [ ] Keep a deterministic starting plan available when AI is unavailable. Never show an invented “analysing your lifestyle” sequence.

Done when: a new user can understand their first plan and begin an action without reading a wall of text; skipped setup can be completed later; saved answers survive interruption. Validate that the chosen routine actually controls the created training plan.

### P1 — Give the interface a recognisable Fitzo style

- [ ] Review onboarding, Home, logging and coach screens together on actual device screenshots; distinguish observed problems from preferences.
- [ ] Define a small visual system: one primary accent, consistent neutral surfaces, a clear type scale, spacing and button hierarchy. Check light/dark appearances independently.
- [ ] Remove decorative glows, stacked gradients, repeated icons and card borders where they add no meaning. Keep motion only where it explains a transition or interaction.
- [ ] Use one obvious main action per screen. Group related content; hide secondary detail behind labelled controls rather than displaying every metric at once.
- [ ] Replace generic labels such as “Your Blueprint” with concrete headings such as “Your starting plan.” Keep body copy short and specific to the user’s actual answers.
- [ ] Show real workout and food examples; avoid invented testimonials, fake precision and generic motivational filler.

Copy examples: “How many days can you train?” / “Here’s your first week” / “You can adjust these targets later.” Use Hinglish where the user chooses it, not as forced decoration.

Done when: the core screens feel like one product, remain readable at larger text sizes and clearly distinguish actions from decoration. A fresh user should be able to explain what to do next without help.

### P1 — Simplify Home into Today

- [ ] Build on existing Home components: lead with today's workout and Start/Adjust actions, one useful food action and a compact progress summary.
- [ ] Move detailed charts, secondary tools and repeated summaries below the main tasks or into their existing destinations.
- [ ] Label incomplete logs and missing readings accurately. Do not frame unlogged food as confirmed under-eating or missing health readings as zero.
- [ ] Use helpful empty states that open the relevant logger directly.

Done when: starting a workout and logging food are obvious from the first screen; existing useful features remain discoverable.

## Second release: trustworthy personalised guidance

### P2 — Reliability, memory and coach actions

- [ ] Measure AI request failures, latency and provider errors without exposing personal prompts or credentials in logs. Recheck current deployment before assuming an old Gemini error is still present.
- [x] Provide useful retry/fallback states; preserve user input when generation fails. Coach restores a failed question without overwriting a newer draft; failed history loading is labelled. Further provider-level fallback work remains separate.
- [ ] Add a user-visible, editable preferences summary: equipment, schedule, dietary preferences and limitations. Define which facts are stored, how they are updated and how users remove them.
- [ ] Turn supported coach suggestions into structured actions with a preview, explicit confirmation and undo where feasible: adjust a workout, save a meal or change a schedule.
- [ ] Validate actions on the server; never apply targets or plan changes directly from unvalidated model text.

Done when: advice uses current saved facts, the user can correct those facts, and proposed changes are understandable before they are applied. Complete the target-source fix before adding automated target changes.

### P2 — Explain health data and recovery

- [x] Show last successful sync, available metrics and source where known, with a manual refresh and useful failure state. The timestamps describe this device's import history; saved reports do not invent source provenance.
- [x] Distinguish importing off, unavailable native services, empty results, incomplete queries, old imports and failed uploads. Empty HealthKit results do not prove permission was denied. The 24-hour freshness message describes import timing, not the age of every saved reading.
- [ ] Verify historical import and background sync on supported physical devices, including repeated imports, timezone boundaries, partial permissions and foreground recovery. Code presence alone is not verification.
- [x] Surface the existing subjective readiness check-in as optional sleep/energy/soreness input, with a simple explanation. Today displays self-ratings and no health/readiness score.

Done when: users know what was imported and how current it is, and denied access does not prevent them using Fitzo.

## Later: practical meal support

- [ ] Suggest a small number of meals using saved dietary preferences, realistic portions and familiar Indian foods.
- [ ] Support portion changes, substitutions and saving meals into the existing logger.
- [ ] Add a grocery list only once meal quantities and substitutions work reliably.
- [ ] Evaluate direct wearable integrations only after measuring demand and gaps in existing Apple Health / Health Connect coverage.

## Verification and measurement

- [ ] Test onboarding with people unfamiliar with Fitzo; record confusing questions and whether they understand their plan. Do not assume competitor onboarding converts better without evidence.
- [ ] Measure completion by stage, time to first workout/meal, abandonment, and repeated errors. Establish a baseline before setting numerical improvement goals.
- [ ] Check small phones, iPad, keyboard overlap, large text, screen-reader labels, contrast and tap targets.
- [ ] Verify back navigation, interruption/resume, optional setup, denied permissions, network failure and AI failure.
- [ ] Regression-check saved targets, existing users and workout creation after any onboarding changes.
- [ ] Run relevant automated checks after implementation; obtain native device evidence for permission and background behaviour before declaring it complete.

## Scope boundaries

Manager features stay deferred. Do not add cognitive games, extra wellness scores, camera form claims or a navigation overhaul just to resemble OxeAI. This checklist creates no release, deployment or App Store submission.
